# T9.15 — `tt` installable and runnable without cloning the repo

- **status:** implementation complete; pending release cut
- **priority:** P0
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §9, new entry `T9.15`.

## Scope

`internal/install`, `cmd/tt`, `Makefile`, `.gitlab-ci.yml`, and the install
sections of `README.md` and `docs/INSTALL.md`. No HTTP contract change, so
nothing here crosses into the KMP client.

A customer who does not want to clone the repo or build anything should be able
to run one `curl` command and have a working server. That means two things:

1. **The `tt` CLI is curl-installable.** A one-liner fetches the static binary
   for the host's platform and puts it on `PATH`.
2. **`tt install --runtime native` can fetch the server binary it supervises.**
   `tt` never phones home, so it cannot download a binary on its own — but an
   operator who explicitly passes `--server-binary-url` can point it at a
   release asset, and `tt` downloads that single file over HTTPS into the data
   directory.

The Docker path is unchanged: `tt install` still pulls the image and bootstraps
the daemon, and cloning the repo is still the supported development path.

**Fixed by the product constraint:** `tt` never phones home, so every URL that
enters the system is an explicit argument the operator chooses. Nothing here
derives a URL from a version, a project endpoint, or a hosted relay. The curl
one-liner in the docs names the URL; `--server-binary-url` names the URL. The
release job publishes the artifacts that URL points at.

## Files

- `internal/install/fetch.go` — `FetchBinary`: HTTPS-only download with a size
  cap, written to a `.part` file and renamed into place, then `0755`.
- `internal/install/fetch_test.go` — tests for the pure function (status codes,
  cap, http refusal, rename, chmod) using `httptest`.
- `cmd/tt/install.go` — `--server-binary-url` flag, the fetch branch in the
  native runtime path, the `fetchBinary` dependency, dry-run output.
- `cmd/tt/install_test.go` — fetch is injectable; tests cover the URL branch.
- `Makefile` — `release-tt` target: builds `tt` + `server` per platform into
  `dist/`, then zips each pair as `tt-<os>-<arch>.tar.gz`.
- `.gitlab-ci.yml` — `release-tt` job in the `release` stage, gated on tag.
- `README.md` — the quick start now begins with the curl one-liner.
- `docs/INSTALL.md` — Step 0 documents the curl path and the native path.
- `docs/PLAN.md` — new `T9.15` row.

## Contract

- [x] `curl -fsSL <url> | tar -xz -C /usr/local/bin` on any supported platform
      yields a working `tt` on `PATH`. The tarball layout is produced by
      `make release-tt`; the URL in the docs is a placeholder until a tag is
      cut and the asset is published.
- [x] `tt install --runtime native --server-binary-url https://.../server` on
      a Linux host with systemd downloads the binary into the data directory,
      supervises it, and never runs `docker`. Tested in
      `TestInstallNativeFetchesTheBinaryFromAURL`.
- [x] `--server-binary-url` with `--runtime docker` is refused (a Docker
      install does not supervise a binary). Tested in
      `TestInstallRefusesServerBinaryURLWithDocker`.
- [x] `--server-binary-url` over `http://` is refused; only `https://` is
      accepted. Tested in `TestFetchBinaryRefusesHTTP` and
      `TestFetchBinaryRefusesNoHost`.
- [x] A download larger than the cap is refused and the partial file is removed.
      Tested in `TestFetchBinaryRefusesOverCap`.
- [x] `--dry-run` with `--server-binary-url` prints the fetch plan and executes
      nothing. Tested in `TestInstallDryRunNamesTheFetchDestination`.
- [x] `--server-binary` still takes precedence over `--server-binary-url` when
      both are passed (`resolveServerBinary` checks the explicit path first).
- [x] Existing Docker installs and the existing tests are unchanged
      (`go test ./internal/install ./cmd/tt` is green).
- [ ] A real download from a release host and a real `systemctl` install are
      recorded as pending: they are environment behaviour, not unit-testable.

## Validation

- `go test -count=1 ./internal/install ./cmd/tt` — the development loop.
- `FetchBinary` is a pure function over an injectable `*http.Client`; the
  runner and filesystem effects are faked in tests.
- Nothing here needs the race detector: no new concurrency.
- `scripts/check.sh` is the release gate and is not run per task.
- Claims a focused run cannot prove (a real download from a release host, a real
  `systemctl` install) are recorded as pending, not claimed.

- **Next step:** cut a tag, run `make release-tt`, and point the docs at the
  published tarball. Then land this branch.
- **Gotchas:** the fetched binary lands in `<data-dir>/<name>/server`, which
  `ensureServiceUser` chowns to the `tasktracker` account — do not put it
  somewhere the service account cannot read. `os.Rename` across filesystems
  fails, so the `.part` file is written in the destination directory. The
  server binary uses CGO for the SQLite driver, so the bundle only runs on the
  host it was built for: `SERVER_PLATFORMS` is Linux/amd64 only today.
