# T10.1 — Agent runs: a queue, a runner credential, and a progress log

- **status:** in-progress
- **priority:** P1
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §Milestone 10, entries `T10.1`–`T10.5`.
  This file is the server half of a dual-repo contract. The client half is
  [`TaskTrackerKMP/specs/11.1-agent-runs.md`](../../TaskTrackerKMP/specs/11.1-agent-runs.md);
  the two must agree key for key before either is implemented.

## Scope

A work item in `in_progress` can be handed to an LLM agent. The agent runs as a
worker on the machine that holds the code (`tt agent run`), not inside this
binary: the server cannot reach a customer's `127.0.0.1:11434`, must not hold an
LLM provider key, and has no working copy to edit. So the server's job is three
things and no more:

1. **Accept a dispatch** from the app and snapshot the task as it is right now.
2. **Queue it** for a runner owned by the requesting user, with a lease so a
   crashed runner does not strand the run.
3. **Store and serve the progress log** the runner appends, so the app can show
   what the agent is doing.

Out of scope, deliberately:

- No LLM call, provider key, or model setting on the server. Every provider
  choice lives in the runner's config on the developer's machine.
- No agent write-back into synced entities. A run reports; it does not move a
  status or post a comment. `Comment.authorID` is a `UserID`, and attributing a
  bot write is a data-model change this task does not make.
- No change to the sync envelope, the change feed, or any existing response.
  Agent state is time-sensitive and non-mergeable, and a new key on `workItem`
  would break every installed client.

## Contract

### Tables (migration 0012)

| Table | Essentials |
| --- | --- |
| `agent_runners` | `id`, `user_id`, `name`, `token_hash` (unique), `provider`, `model_label`, `last_seen_at`, `revoked_at`, `created_at` |
| `agent_runs` | `id`, `work_item_id`, `project_id`, `requested_by`, `runner_id`, `status`, `cancel_requested`, `task_document`, `lease_expires_at`, `summary`, `error`, `created_at`, `started_at`, `finished_at` |
| `agent_run_events` | `(run_id, seq)` primary key, `kind`, `message`, `payload`, `created_at` |

- `status` is `queued | claimed | running | succeeded | failed | cancelled`,
  enforced by a `CHECK` in both dialects.
- A partial unique index on `agent_runs (work_item_id) WHERE status IN
  ('queued','claimed','running')` is what enforces "one live run per work
  item". Two devices can race a dispatch; the app's `409` is derived from this
  index, not from a read-then-write check that both can lose.
- `task_document` is an opaque JSON string (the snapshot the runner receives),
  stored and re-served verbatim. A runner older than the server must still
  decode the job it is given, so the task never becomes typed columns that
  would later gain a field.

Timestamps are epoch milliseconds in the database and ISO-8601 UTC whole
seconds on the wire for this API, matching entity payloads and
`internal/entities/timestamp.go`.

### Runner API — opaque token, `Authorization: Bearer ttag_…`

A runner token is not a user JWT. It is an opaque random value, stored only as
a hash, scoped to the `user_id` that registered it, revocable row by row, and
refused by every user route. A dedicated middleware resolves it; `Auth` must
not accept it.

| Route | Behaviour |
| --- | --- |
| `POST /v1/agent/runs/claim` | Claims the oldest `queued` run **requested by this runner's user**, in a project that user is a member of. Long-polls up to `waitSeconds` (default 25, max 30), then `204`. Sets `lease_expires_at`. |
| `POST /v1/agent/runs/{id}/events` | Appends `{events:[{kind,message,payload}]}`; server assigns `seq` and answers `{accepted, nextSeq}`. |
| `POST /v1/agent/runs/{id}/heartbeat` | Extends the lease, answers `{cancelRequested, leaseExpiresAt}`. |
| `POST /v1/agent/runs/{id}/finish` | `{outcome:"succeeded"\|"failed"\|"cancelled", summary, error}`; terminal, idempotent by status. |

### App API — user JWT, project-membership scoped

| Route | Behaviour |
| --- | --- |
| `POST /v1/agent/runs` | `{"workItemId":"…"}` → `201` run. `409` when a live run exists; `403` for a non-member; `409`-class refusal when the item is not `in_progress`. |
| `GET /v1/agent/runs?workItemId=…&limit=20` | Recent runs, newest first. |
| `GET /v1/agent/runs/{id}?afterSeq=0` | `{run, events, hasMore}` — one round trip for the progress sheet. |
| `POST /v1/agent/runs/{id}/cancel` | Sets `cancel_requested`; the runner observes it at its next heartbeat (≤10 s) and finishes `cancelled`. |
| `POST /v1/agent/runners` | Registers this machine and returns the token **once**. |
| `GET /v1/agent/runners` | The caller's own machines, including revoked ones. |
| `DELETE /v1/agent/runners/{id}` | Revokes one of the caller's own runners. |

### Response shapes

`run`:

```json
{
  "id": "…",
  "workItemId": "…",
  "projectId": "…",
  "status": "running",
  "requestedBy": "…",
  "runnerId": "…",
  "cancelRequested": false,
  "createdAt": "2026-11-03T12:00:00Z",
  "startedAt": "2026-11-03T12:00:07Z",
  "finishedAt": "",
  "summary": "",
  "error": ""
}
```

`event`:

```json
{ "seq": 41, "kind": "status", "message": "Editing TT-12", "payload": "{}", "createdAt": "2026-11-03T12:00:09Z" }
```

Every key the client declares without a default is always present; `runnerId`,
`startedAt`, `finishedAt`, `summary` and `error` are declared with defaults on
the client side, so they may be empty or omitted. `payload` is an opaque JSON
string so a new event kind never changes this key set.

- **Gotchas:**
  - The DDL and the repository belong in the same commit
    (`go-migrations-and-repositories`), so T10.1 stays one branch.
  - The one-live-run rule is the partial index, not a handler check. Do not add
    a read-then-write guard in front of it; a claim race must be resolved by the
    database.
  - **Placeholders must ascend in text order.** go-sqlite3 numbers parameters by
    appearance, not by the `$n` suffix. A statement whose `$n` values appear as
    `$2, $1, $3` binds the wrong argument and silently matches no rows — this
    cost a debugging round on `finish`, `heartbeat` and `revoke`. Postgres does
    not care, so the bug only shows on SQLite.

    `token_hash`; runner inserts name `token_hash` explicitly. Do not reuse the
    read list for an insert.
  - `AppendEvents` treats its batch as a heartbeat, so a long tool call does not
    look like a dead runner. Cancel is observed on a heartbeat, up to one beat
    later.
  - `Claim` clears the write deadline with `http.NewResponseController`. The
    server's 15 s `WriteTimeout` would otherwise cut a 25 s poll; keep that call
    if the handler is touched.
  - The `mount` signature gained `agentHandler`. `cmd/server/contract_test.go`
    and `cmd/server/main_test.go` were updated for it — the only files edited
    outside this spec's original list.
  - `cmd/tt/main.go` resolves `install.DefaultStatePath()` before the command
    switch. `tt agent` must not require install state; give it its own config.
  - Claim scope is the runner owner's own runs. A teammate's machine silently
    executing your task is not the default; `--shared` is later.
  - Runner tokens are hashed at rest and returned once. Never log one.

## Risks / notes

- **Prompt injection is a real boundary here.** Work item text is untrusted
  input to a process that can run commands. The runner needs an explicit
  `--workspace`, a `--read-only` mode, and per-action approval; the server
  holds no execution authority at all.
- **Event volume:** a chatty agent can write thousands of rows per run. Batch on
  the runner (about 1 s or 20 events) and prune by
  `AGENT_EVENT_RETENTION` (default 720 h), mirroring `SYNC_LOG_RETENTION`.
- **Cancel is cooperative.** Do not delete a run to stop it; the record is the
  audit trail and the one-live-run slot must be released by a terminal status.
- **Lease drift:** extend on every event batch as well as on heartbeat, so a
  long tool call is not mistaken for a dead runner.
