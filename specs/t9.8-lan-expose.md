# T9.8 — `tt expose --provider=lan` (default)

- **status:** done
- **priority:** P0
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §Milestone 9 — Customer install and
  exposure, entry `T9.8` — the *what* and the rationale live there; this file is
  the *how*.

## Scope

Make the installed server reachable from the customer's local network, verify it
from the host's own LAN address, and print the pairing link only after that
check. Server-only work: no HTTP endpoint, no wire-format change, and no
install-state schema change.

**File-list drift.** The archive names `cmd/tt/`, `docker-compose.yml`, and
`docs/SELF-HOSTING.md`. The customer compose is no longer the root developer
stack: T9.4/T9.5 generate it from
`internal/install/embed/docker-compose.tmpl`, so that template is the
`docker-compose.yml` this task changes. The root `docker-compose.yml` is the
developer stack and stays loopback-only; opening it would expose every
contributor's test server. T9.6's handoff explicitly requires `checkAddress` to
change here, so `internal/install/checks.go` is in scope by dependency.

**Exposure is not persisted in `install.State`.** `tt expose` writes the
LAN publish into the rendered compose and verifies it; `tt install` renders
loopback and therefore resets the exposure. This keeps the state schema and its
strict `DisallowUnknownFields` contract unchanged, and makes a repair return to
the safe default. The docs say to re-run `tt expose` after a repair. The T9.6
note that `tt expose` records a public hostname is satisfied for LAN by
re-detecting the address on each run; a stable persisted hostname belongs to
T9.9/T9.10, where the provider names it.

**Non-LAN providers are refused.** `--provider=tailscale` and
`--provider=cloudflare` print that they arrive in T9.9/T9.10 and make no
change. Falling back to LAN would expose a host the customer did not ask to
expose.

## Contract

- [x] `tt expose` defaults to `--provider=lan`; the flag accepts the three
      provider names. `tailscale` and `cloudflare` exit 1 with a message naming
      T9.9/T9.10 and invoke neither the runner nor the verifier. An unknown
      provider is refused with the same three-name message.
- [x] The install state's provider must match the requested provider; a
      tailscale/cloudflare install is refused rather than quietly published
      with LAN.
- [x] A missing or corrupt install state is a clear error; `tt expose` does not
      create an install. A corrupt state is refused, not overwritten.
- [x] The LAN address is detected through `install.LANAddress`; an empty,
      loopback, or unspecified address is refused before any file is written.
- [x] The exposed compose publishes `0.0.0.0:<state port>:8080` and keeps
      `SERVER_BIND: "0.0.0.0"` inside the container. It still carries the same
      image tag, database URL, and secrets as the loopback compose; only the
      host side of the publish differs.
- [x] The compose is written atomically through `StepWriteCompose`, then
      `docker compose up -d` runs through `StepComposeUp`.
- [x] Verification is an HTTP GET to
      `http://<detected LAN address>:<state port>/readyz` — never
      `127.0.0.1`. The verifier polls until 200 or the timeout expires.
- [x] A failed `compose up` or a failed LAN verification restores the previous
      compose bytes and runs `compose up -d` again before exiting 1. The
      pairing link is printed only after a successful verification.
- [x] Success prints the LAN URL, a trusted-LAN/plain-HTTP warning, and the
      `tasktracker://connect` link plus QR through the existing `printPairing`.
      No install secret is printed.
- [x] `tt install` still renders loopback. The docs state that a repair resets
      an exposure and that `tt expose` must be re-run.
- [x] `checkAddress` reports `published at 127.0.0.1:<port> (this host only)` or
      `published at 0.0.0.0:<port> (LAN)` as OK, and still fails any other
      host, the IPv6 wildcard, and a missing host publish.
- [x] The provider check remains a `skip`; it is not turned green merely
      because `tt expose` ran. Its fix names the LAN verification and the
      later provider checks.
- [x] No wire-format, database, or configuration change.

## Handoff

- **Done:** `tt expose --provider=lan` is implemented. It refuses non-LAN and
  mismatched providers, detects and validates the LAN address, renders and
  applies the all-interfaces publish, verifies `/readyz` at that address, rolls
  back to the previous compose on failure, and prints the pairing link and QR
  only after verification. `checkAddress` accepts the loopback and LAN
  publishes; `WaitReady` is shared with the install runner; the docs cover the
  plain-HTTP/trusted-LAN and Android cleartext caveats.
- **Verified:** `scripts/check.sh` green; focused tests green; cross-builds
  green; five mutation checks failed as named and were reverted; a rendered
  exposed compose passed `docker compose config`.
- **Pending:** push and MR authorization. No PR is open yet.
- **Next step:** push `feat/t9.8-lan-expose`, open the MR, then T9.9
  (`tt expose --provider=tailscale`).
- **Gotchas:**
  - The generated customer compose is the embedded template, not the root
    `docker-compose.yml`; the root developer stack stays loopback.
  - `SERVER_BIND` is already `0.0.0.0` inside the container; the missing half
    was the host publish.
  - The exposure is not in `install.State`. `tt install` re-renders loopback,
    so a repair resets it and the docs say to re-run `tt expose`.
  - The verification address comes from `LANAddress`, not the loopback
    constant. A loopback check passes even when the publish is wrong, which is
    the exact mistake T9.8 exists to catch.
  - A state whose provider is tailscale/cloudflare is refused by `tt expose`
    until T9.9/T9.10, even though `tt install` accepts the flag.

## Risks / notes

- `tt expose` is deliberately not persisted: the compose file is the exposure,
  and a repair returns to the safe default. The cost is that a repair needs a
  second command; the benefit is no install-state schema change and no silent
  wide publish after an upgrade.
- `checkAddress` cannot tell an intentional `0.0.0.0` from an accidental one
  without a state field. It names the mode in the summary so the operator sees
  it; any other host is still a failure.
- The verification uses `/readyz`, not `/healthz`, so a database outage fails
  an expose and triggers the rollback. Printing a pairing link for a server
  that cannot serve a request would be worse than a failed command.
- The root developer compose is unchanged. A contributor who needs a phone on
  the same LAN can use `tt` against a disposable state, not the shared dev
  stack.
