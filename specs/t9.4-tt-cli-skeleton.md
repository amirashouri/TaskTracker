# T9.4 — `tt` CLI: skeleton, state file, and idempotence

- **status:** done
- **priority:** P0
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §Milestone 9 — Customer install and
  exposure, entry `T9.4` — the *what* and the rationale live there; this file is the *how*.

## Scope

A new `cmd/tt` binary in this module plus the state machine it drives. No server
behaviour change, no wire-format change. The state machine must be testable **without
Docker**, which is what makes this a normal task rather than an integration test.

## Files

Confirmed at Phase 1. **Decision:** no prompt/TUI dependency. Subcommands are dispatched
from `os.Args` with the standard `flag` package; the wizard will read stdin with plain
prompts. `go.mod` is unchanged.

- `cmd/tt/main.go` — the composition root: parse the command, load state, dispatch.
  Mirrors `cmd/server/main.go`'s shape (a `switch` on `os.Args[1]`, subcommands in their
  own files) rather than pulling in a CLI framework.
- `cmd/tt/install.go`, `cmd/tt/status.go`, `cmd/tt/uninstall.go` — one subcommand group
  per file; `main.go` keeps dispatch and the shared helpers.
- `internal/install/state.go` — the state file: instance name, mode, provider, paths,
  image tag, state schema version, and the generated secrets. JSON, `0600`, written
  atomically (temp file + rename).
- `internal/install/plan.go` — the state machine: `func Next(state State, cmd Command)
  ([]Step, error)`, a pure function. This is the file the tests own.
- `internal/install/compose.go` — renders the embedded compose template from a `State`;
  the only place the CLI injects the image tag, secret, and database URL.
- `internal/install/runner.go` — the adapter that executes a `Step`; the only place that
  shells out to `docker compose`. Behind an interface so `plan.go`'s tests never touch it.
- `internal/install/embed.go` and `internal/install/embed/` — `go:embed` of the CLI
  compose template, the systemd unit, and the `Caddyfile`. Embedded rather than read
  from the working directory: the CLI is run from wherever the customer downloaded it.
  A test keeps the embedded systemd unit byte-identical to `deploy/tasktracker.service`.
- `cmd/tt/main_test.go`, `internal/install/plan_test.go`, `internal/install/state_test.go`.
- `Makefile`, `.gitlab-ci.yml`, `.gitignore` — a release job for the static builds
  (darwin/linux/windows × amd64/arm64), with `dist/` ignored.

## Contract

- [x] `Next` is pure: given a state and a command it returns the same steps, and its tests
      run with no Docker daemon and no network.
- [x] **Idempotence:** `install` twice against the same state produces `repair`, never
      `init`. Asserted on the returned step list, not on a rendered message.
- [x] **The secret is generated once.** A second `install` leaves `JWT_SECRET` byte-for-byte
      unchanged; the test seeds a state with a known secret and asserts it survives.
- [x] **The image tag is the CLI's own version**, so `tt upgrade` cannot pull a server
      newer than the binary driving it. A test pins that the rendered compose contains the
      tag the build reports.
- [x] `--dry-run` prints the rendered compose and executes nothing — asserted by the runner
      never being called.
- [x] A corrupt or partially written state file is reported and refused, not silently
      replaced. (The atomic write means a crash leaves the *old* file, so this is the
      case where the file was hand-edited.)
- [x] `uninstall` without the instance name typed back exits non-zero and removes nothing.

## Validation

- Run: `go test ./cmd/tt/... ./internal/install/...` while iterating.
- `scripts/check.sh` — green at the release gate.
- `scripts/check.sh race` — green. The CLI has no shared concurrent state; the race run is
  the release gate's sweep, not a claim that the installer is concurrent.
- `gofmt -l .` — no output.
- Focused tests were confirmed to fail when the behavior they protect is removed: repair
  reusing the command's replacement secret, `--dry-run` executing steps, uninstall
  accepting a wrong name, the image tag being hard-coded, repair defaults being removed,
  and the port-change refusal being removed.
- Rendered compose for both `sqlite` and `postgres` validates with
  `docker compose config` (run by hand; CI has no daemon).
- The Docker-touching path was exercised by hand with a fake `docker` adapter and a local
  `/readyz` listener: the first install wrote state and compose as `0600`; the second
  preserved the secret byte-for-byte and printed no secret; a wrong-name uninstall made
  zero Docker calls and left the state; the correct-name uninstall removed the state.

- **Next step:** T9.5 (`tt install` wizard): preflight, profile choice, admin bootstrap,
  URL/QR, LAN warning. Extend `Command`/`Step` for wizard decisions; do not move shelling
  out back into `cmd/tt`.
- **Gotchas:**
  - `install` on an existing state is a repair and preserves the recorded image tag. A
    later `tt upgrade` is the only path that changes it, so a repair cannot silently pull
    a server newer than the binary that planned it.
  - Repair defaults come from the existing state when flags are omitted, so `tt install`
    with no flags repairs a Postgres instance instead of replacing it with the new-install
    SQLite default. An explicit mode/provider/data-dir/port change is refused.
  - The embedded systemd unit is a copy of `deploy/tasktracker.service`; the test fails if
    they drift.
  - The state file holds the JWT and database secrets. It and the rendered compose are
    both `0600`; the compose uses named Docker volumes so the host data directory does not
    need container-UID ownership.
  - The CLI and the server must share a module (they do) so the version is one value. Do
    not create a second `go.mod` under `cmd/tt` — that would let the two drift.

## Risks / notes

- Easy to get wrong: making `install` a script with `if` statements. The state machine is
  what makes "resume after a failure halfway through" testable; a script makes it
  untestable and the resume path is exactly where a non-technical user gets stuck.
- Do not embed the compose file from the working tree at runtime and the embedded copy at
  release time — one source, `go:embed`, always.
