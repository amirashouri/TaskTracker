## Scope

Add Cloudflare Tunnel exposure via a `cloudflared` sidecar in Docker Compose.
The command requires a customer-owned domain on Cloudflare, walks through
creating a tunnel and API token, verifies the public hostname, and configures
`TRUSTED_PROXIES` to the compose subnet. The 100 MB Cloudflare request-body cap
is enforced against `ATTACHMENT_MAX_BYTES` at startup.

Server-only work: no HTTP endpoint change, no wire-format change, no
install-state schema change. The server stays on loopback; `cloudflared`
terminates TLS and proxies to it.

**File-list drift.** The archive names `cmd/tt/`, `docker-compose.yml`,
`internal/config/config.go`, and `docs/SELF-HOSTING.md`. The compose template is
`internal/install/embed/docker-compose.tmpl` (established by T9.4/T9.5/T9.8).
This task extends it with a `cloudflared` service and provider-specific trusted
proxies.

## Contract

- [ ] `tt expose --provider=cloudflare --domain <hostname>` is accepted. Unknown provider still gets the provider list.
- [ ] The install state's provider must be `cloudflare`. A LAN/Tailscale state asked to expose as Cloudflare is refused before any Cloudflare command or compose step; message names matching provider command and reinstall path.
- [ ] If `cloudflared` is absent from `PATH`, the command prints a platform install hint and exits 1 without running tunnel commands, composing, or changing the state.
- [ ] Domain validation: refuses a hostname whose zone is not on Cloudflare; explains registrar change and DNS propagation delay. Does not pretend automation exists for this step.
- [ ] `cloudflared tunnel create` / `cloudflared tunnel route dns` run via customer's API token. Token stored in OS keychain (preferred) or `0600` file at `~/.config/tasktracker/cloudflare-token`; never in compose file or state.
- [ ] Compose written for a cloudflare state: publishes `127.0.0.1:<port>:8080`, adds `cloudflared` service with tunnel token, contains `TRUSTED_PROXIES` set to the compose subnet (e.g., `172.18.0.0/16` — derived from the compose network).
- [ ] After compose up, command requests `https://<domain>/readyz` with certificate verification. Only on success prints the URL and `tasktracker://connect` pairing link/QR.
- [ ] Failed HTTPS verification prints the URL, says the Cloudflare configuration is still active, names cleanup commands. Does not print pairing link.
- [ ] `ATTACHMENT_MAX_BYTES` validated at startup: if provider is `cloudflare` and value exceeds 100 MB (104857600 bytes), refuse with message naming Cloudflare's 100 MB cap.
- [ ] Successful command prints the public URL, states server stays on loopback behind Cloudflare Tunnel, prints cleanup commands.
- [ ] `tt install --provider=cloudflare` installs loopback server and points at `tt expose --provider=cloudflare --domain <...>`.
- [ ] `tt doctor` gives a Cloudflare command to verify the URL.
- [ ] No wire-format, HTTP response, database, or install-state schema change.

## Risks / notes

- Cloudflare Free plan has a 100 MB request-body limit. If the customer sets `ATTACHMENT_MAX_BYTES` higher, uploads fail with a 413 from Cloudflare that never reaches the server logs. The startup validation catches this early.
- DNS propagation for the new CNAME can take minutes to hours. The command verifies with retries but does not wait indefinitely.
- `cloudflared` auto-updates by default. The compose should pin the version or document the update behavior.
- The tunnel token is a secret. The CLI must not log it. The OS keychain is preferred; the `0600` file fallback must be clearly documented.
- The compose subnet CIDR varies by Docker daemon configuration. Derive it at render time from the network the services share, or use a fixed `/16` that matches the default bridge behavior.
