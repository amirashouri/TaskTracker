# T9.5 — `tt install`: the interactive wizard

- **status:** done
- **priority:** P0
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §Milestone 9 — Customer install and
  exposure, entry `T9.5` — the *what* and the rationale live there; this file is the
  *how*.

## Scope

Wrap T9.4's install state machine in the path a non-technical customer follows:
preflight, profile choice, data-directory confirmation, admin bootstrap, and a
working URL. Server-only work: no HTTP endpoint and no wire-format change.

**Explicitly deferred:**

- **QR / `tasktracker://connect` link:** T9.7, after the client can accept a
  runtime URL. T9.5 prints the URL and the next step only.
- **LAN publishing:** T9.8. The compose publish remains loopback-only; T9.5
  prints the host's detected LAN address as the address T9.8 will publish, not
  as a currently reachable URL.
- **Guided Docker bootstrap:** T9.12. If Docker is absent T9.5 prints the
  official install URL and the start hint, and exits without changing anything.
- **Lid/battery/Wi-Fi detection:** T9.5 prints a conservative laptop warning for
  `lan` installations. Detecting the physical host state is unreliable across
  the three release platforms and a false negative is worse than a short note.

## Files

- `cmd/tt/main.go` — pass stdin to `install`, update usage, keep dispatch thin.
- `cmd/tt/install.go` — flag parsing and the wizard flow. No Docker shell-outs.
- `cmd/tt/wizard.go` — prompt loops, input validation, and the URL/LAN output
  helpers extracted from `install.go` to keep the flow file readable.
- `cmd/tt/prompt.go` — stdin prompter and TTY detection. Password reads preserve
  whitespace; the terminal still echoes them because hidden input needs a new
  dependency. `go.mod` stays unchanged.
- `cmd/tt/install_test.go` — wizard tests with fake preflight/prompter/LAN
  detection and a recording runner.
- `cmd/tt/main_test.go` — adapt T9.4 install tests to inject a successful
  preflight; keep the `--dry-run` and non-install coverage.
- `internal/install/preflight.go` — Docker binary/daemon, data-directory
  writability, port, and disk checks with an injectable environment. Errors name
  the fix, not only the symptom.
- `internal/install/preflight_test.go` — table tests for every failure and the
  repair port exemption.
- `internal/install/disk_unix.go`, `internal/install/disk_windows.go` —
  available-space probe. Windows reports "unknown" (zero), so the check is
  skipped rather than blocking an install.
- `internal/install/lan.go`, `internal/install/lan_test.go` — pick a
  non-loopback IPv4 LAN address, preferring RFC 1918 addresses and skipping
  virtual interfaces.
- `internal/install/plan.go` — `AdminBootstrap`, admin command fields, and the

- `internal/install/plan_test.go` — admin step placement, half-credentials

- `internal/install/runner.go` — execute the admin step through
  `docker compose exec -T server /app/server user-create`; add a small command
  seam so tests never need Docker; redact the password from errors.
- `internal/install/runner_test.go` — exact admin command, no-display-name
  variant, and password redaction.
- `specs/t9.5-install-wizard.md`, `docs/PLAN.md` — status and handoff.

## Contract

- [x] Preflight checks the Docker binary and daemon, the data directory's
      writability, the host port on a new install, and free space. Every failure
      names the fix (install URL, start hint, `--data-dir`, `--port`, or free
      space) and no state, compose file, or container is written.
- [x] A repair skips the port check, skips admin bootstrap, and preserves the
      T9.4 secret and recorded image tag.
- [x] An interactive run prompts for `sqlite` (the default) or `postgres` and
      confirms the data directory. A non-interactive run uses flags/defaults,
      requires `--admin-email` and `--admin-password`, and `--yes` forces the
      non-interactive path.
- [x] The first admin is created through the existing `server user-create`
      subcommand via `docker compose exec -T server /app/server user-create … --admin`.
      No HTTP endpoint is added.
- [x] The password does not appear in a runner error or success message. The
      argv exposure inherited from `user-create --password` is documented, not
      silently ignored.
- [x] `lan` installations print the detected LAN IPv4 address and a warning
      about laptop sleep, battery, Wi-Fi, and a closing lid. Non-LAN providers
      print that they are not implemented yet instead of pretending the URL is
      reachable.
- [x] `--dry-run` prints the rendered compose and calls no preflight, no
      prompter, no runner, and writes no state. It remains usable with no Docker
      daemon.
- [x] The first-install secret is printed when the state write succeeds, before
      the server/admin steps that can fail, so a failed `/readyz` or admin
      bootstrap does not lose it.
- [x] All tests run without a Docker daemon: preflight uses a fake environment,
      the wizard uses a fake prompter and preflight, and the admin command uses
      a recording command runner.

## Handoff

- **Done:** T9.5 is implemented and validated. The preflight, interactive and
  non-interactive wizard paths, admin bootstrap, LAN output, repair behavior,
  secret timing, and `--dry-run` isolation are covered by tests. The branch is
  ready to merge.
- **Pending:** nothing in T9.5. Push/merge needs authorization.
- **Next step:** merge `feat/t9.5-install-wizard`, then T9.6 (`tt doctor` and
  `tt status`).
- **Gotchas:**
  - `--dry-run` must stay before preflight, prompts, and runner execution. It is
    the only path that works on a machine with no Docker daemon.
  - The first-install secret is printed immediately after `StepWriteState`, not
    at the end. Moving it back would lose the secret when `/readyz` or the admin
    step fails.
  - The admin password is passed to the existing `user-create --password` flag,
    so it is visible in host/container argv; errors are redacted and the state
    never stores it. The interactive prompt also echoes it. A future
    `--password-stdin`/hidden-input change would close both gaps.
  - A repair never bootstraps an admin. If a first install fails at the admin
    step, use the `docker compose exec` command shown by the runner error; T9.5
    deliberately does not add a second `tt admin-create` path.
  - The compose publish is still loopback-only. The printed LAN address is
    T9.8's target, not a live URL; the QR/`tasktracker://connect` link is T9.7.
  - Preflight disk checking uses the Docker root on Linux (falling back to the
    data directory when it is unreadable) and the data-directory filesystem on
    macOS/Windows. Windows reports disk space as unknown and skips the check.
  - The fake-Docker e2e must put an executable named `docker` on `PATH` and
    isolate `HOME`; otherwise it will either find the real Docker or write to the
    developer's real install state.

## Risks / notes

- Easy to get wrong: treating "Docker is missing" as a crash. It is a supported
  outcome with instructions; T9.12 will offer the guided install later.
- The preflight is intentionally conservative. The data-directory disk check on
  macOS/Windows is a proxy for the Docker Desktop VM disk; on Linux it uses the
  Docker root when it is readable and falls back to the data directory.
- The Linux default state path is `/etc/tasktracker` and the default data
  directory is `/var/lib/tasktracker`; both normally need root. Preflight names
  a writable `--data-dir` fix, but a non-root run can still reach the state
  write and fail there. T9.13 should document `sudo` or the intended ownership;
  a state-path preflight is a reasonable follow-up.
- An admin failure leaves the server installed and the state written. The
  operator has the secret and the redacted command, and a repair can restore the
  server; the CLI exits non-zero so a script cannot mistake it for complete.
