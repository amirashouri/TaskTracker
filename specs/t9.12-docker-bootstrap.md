## Scope

When `tt install` detects that Docker is not installed or its daemon is not
reachable, instead of just printing a hint and exiting, it offers to install
Docker via the distribution's package manager. This is the only place in the
CLI that changes host software, so consent rules are strict:

1. Never automatic, never default-yes. Prompt defaults to `No`; bare Enter
   declines. `--dry-run` prints the command and executes nothing. Non-interactive
   `tt install --yes` **fails closed**.
2. No `curl | sh`. Never pipe a remote script into a shell. Use the
   distribution's package manager from its own repositories. Where the convenience
   script is the practical answer, the CLI *prints* it for the customer to run.
3. Three distributions, then stop: Debian/Ubuntu (apt), Fedora/RHEL family
   (dnf/yum), Arch (pacman). Anything else: print the official URL and exit.
4. Privilege is stated, not assumed. Customer sees the exact command and `sudo`
   it needs before it runs. If `sudo` is missing or wants a password the CLI
   cannot supply, print the command and stop. Joining the `docker` group is
   root-equivalent, so it's a separate explicit yes/no.
5. Verify, then hand back. Start the daemon, wait for `docker info`, then resume
   preflight. Failed install relays the package manager's output and rolls
   nothing back; CLI does not uninstall a package the customer's OS owns.

**Files:** `cmd/tt/install.go`, `internal/install/docker.go` (detection and
command selection — pure function of `os-release`, `docker` presence, and
`sudo` availability), `internal/install/exec.go` (executor interface over
`os/exec`).

## Contract

- [ ] `tt install` on a host without Docker: detects distribution, prints the
      exact `sudo apt/dnf/pacman install ...` command, prompts with default `No`
- [ ] `--dry-run` prints the command and executes nothing
- [ ] `tt install --yes` (non-interactive) fails closed with a clear message
      when Docker is missing
- [ ] Debian/Ubuntu: `sudo apt update && sudo apt install -y docker.io`
- [ ] Fedora/RHEL: `sudo dnf install -y docker` (or `yum` on older)
- [ ] Arch: `sudo pacman -S --noconfirm docker`
- [ ] Other distributions: prints official Docker install URL and exits
- [ ] If `sudo` missing or prompts for password: prints command and stops
- [ ] After install: starts Docker daemon (`sudo systemctl start docker` or
      starts Docker Desktop), waits for `docker info`, then resumes preflight
- [ ] Docker group membership: separate explicit yes/no prompt (not automatic)
- [ ] Failed install: relays package manager output, rolls nothing back
- [ ] No `curl | sh` anywhere; no remote script execution

## Risks / notes

- The customer may not have `sudo` privileges. The CLI must detect this and
  print the command without running it.
- Some distributions may have Docker in a different package name (e.g.,
  `docker-ce` vs `docker.io`). Use the distribution's default repository
  package.
- Docker Desktop on macOS/Windows doesn't use `systemctl`. The start command
  differs by platform.
- The preflight already has `dockerInstallHint` and `dockerStartHint` — these
  become the basis for the guided install but with stricter consent.
- The `--dry-run` flag must work on a machine with no Docker and leave no state
  behind (already works for the compose render; must also work for Docker
  install commands).
